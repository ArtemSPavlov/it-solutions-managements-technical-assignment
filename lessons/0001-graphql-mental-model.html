Схема → запрос → resolver → ответ

Общая модель GraphQL на реальном API цифровой визитки.

10–15 минут · источник: официальная документация GraphQL и NestJS

Результат урока. Ты сможешь прочитать запрос profile { name skills { name } }, предсказать форму ответа и назвать метод проекта, который начинает получение данных.

1. Что такое GraphQL

GraphQL — язык запросов к API и серверный механизм их выполнения. Это не язык запросов к PostgreSQL и не графовая база данных. GraphQL не навязывает способ хранения: данные может предоставить Prisma, другой сервис или обычный объект в памяти (официальное введение).

Для этого проекта полезна модель из четырёх частей:

Схема

Контракт: какие объекты и поля вообще можно запросить.

Запрос

Выбор клиента: какие из разрешённых полей нужны сейчас.

Resolver

Код сервера: где получить значение запрошенного поля.

Ответ

JSON, структура которого повторяет выбранные поля запроса.

2. Схема — контракт API

Вот сокращённая версия файла src/schema.gql:

type Query {
  profile: Profile!
}

type Profile {
  name: String!
  description: String!
  skills: [Skill!]!
  experience: [Experience!]!
}

type Skill {
  name: String!
}
  • Query — корневой объектный тип операций чтения.
  • profile: Profile! — запрос profile возвращает один объект Profile, а не список; ! означает Non-Null.
  • skills: [Skill!]! — всегда список, возможно пустой; его элементы тоже не null.
  • String — скаляр, листовое значение. Profile и Skill — объектные типы с собственными полями.

Схема ограничивает запросы: нельзя обратиться к полю, которого у соответствующего типа нет. Сервер проверяет документ по схеме до выполнения (Schemas and Types, Validation).

В текущей схеме нет Mutation и Subscription: API предоставляет только чтение профиля. Отсутствие изменений — решение контракта, а не ограничение самого GraphQL.

3. Запрос выбирает форму ответа

Клиент не просит «весь профиль целиком». Он строит selection set — набор нужных полей — от корня до скаляров:

query BusinessCard {
  profile {
    name
    skills {
      name
    }
  }
}

query — тип операции, BusinessCard — её имя для диагностики. У объектов profile и skills есть вложенные selection set; у скалярных name их нет (официальный раздел Queries).

Результат имеет знакомую запросу форму:

{
  "data": {
    "profile": {
      "name": "Артём Павлов",
      "skills": [
        { "name": "TypeScript" }
      ]
    }
  }
}

Здесь нет description, links, experience и projects: клиент их не выбрал. Отдельные HTTP-маршруты вроде /profile/skills для этого не нужны — вложенные данные запрошены в одной GraphQL-операции.

4. Как сервер получает данные

При выполнении GraphQL проходит по выбранным полям. Значение поля предоставляет resolver; итог собирается снизу вверх и обычно возвращается как JSON (Execution).

  1. Клиент отправляет операцию на POST /graphql.
  2. GraphQL проверяет запрос по схеме.
  3. Для корневого Query.profile вызывается ProfileResolver.profile().
  4. Resolver вызывает ProfileService, затем ProfileRepository читает профиль и выбранные связи через Prisma.
  5. GraphQL формирует data.profile только с запрошенными полями.
@Resolver(() => Profile)
export class ProfileResolver {
  @Query(() => Profile)
  async profile(@Info() info: GraphQLResolveInfo) {
    return this.profileService.getProfile(
      getProfileSelection(info),
    );
  }
}

Декоратор @Query связывает метод с корневым полем схемы. В проекте явный resolver написан только для этого корня: метод возвращает объект профиля с выбранными связями, из которого GraphQL собирает остальные поля. Параметр @Info() содержит сведения о запросе; проект использует их, чтобы не загружать невыбранные связи. Это тема отдельного урока.

5. Почему модели и схема совпадают

Проект применяет code-first: TypeScript-классы с декораторами @ObjectType и @Field являются источником GraphQL SDL, а src/schema.gql генерируется автоматически. Поэтому его не редактируют вручную (NestJS: code first).

Практическое следствие: чтобы понять публичный контракт, смотри на profile.models.ts и profile.resolver.ts. Чтобы удобно увидеть уже сгенерированный контракт целиком — на schema.gql.

6. Практика: сначала предскажи, потом проверь

Не выполняя запрос, ответь: какие ключи будут у каждого элемента experience и появится ли position?

query BusinessCard {
  profile {
    name
    experience {
      company
      startedAt
    }
  }
}
Показать ожидаемую форму

У каждого элемента будут только company и startedAt. Поля position не будет: GraphQL не подставляет незапрошенные поля.

Если проект запущен, открой Apollo Sandbox, выполни запрос и сравни результат со своим прогнозом. Затем удали startedAt и ещё раз предскажи изменение ответа до нажатия Run.
